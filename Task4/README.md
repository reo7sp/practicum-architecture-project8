# Задание 4. Проектирование продажи ОСАГО

## osago-aggregator

### osago-aggregator и хранилище

Своё хранилище нужно: заявки, идентификаторы у страховщиков, статусы опроса, ответы, идемпотентность при повторах и аудит.

### API osago-aggregator для core-app

`core-app` запускает подбор; агрегатор параллельно обращается к REST каждой страховой компании и не собирает «одним куском» ответ в конце. Каждый пришедший оферт отправляется в общий брокер сообщений из Task 3; `core-app` подписан и отображает пользователю по мере поступления. Синхронный REST со всем списком предложений не используем.

### Интеграция core-app <-> osago-aggregator

Асинхронно через брокер.

### API core-app для веб-приложения

Создание заявки с данными об автомобиле: REST. Обновление экрана с предложениями по мере ответов страховщиков: Websocket от `core-app` к браузеру.

### Интеграция веб-приложение <-> core-app

REST для формы и старта сценария. Websocket для отображения офферов в реальном времени.

### Отказоустойчивость

- Timeout - до 60 с на HTTP-вызов к API страховщика; на межсервисные вызовы - свои, более короткие лимиты.
- Retry - ограниченное число попыток с backoff, но только там где безопасно ретраить.
- Circuit Breaker - к API страховщика.
- Rate Limiting - на входе в публичный API под пик порядка 2500 одновременных сессий; при необходимости квоты на исходящие запросы к страховщикам.

### Несколько экземпляров сервисов

Состояние сессии и ответов страховщиков лежит в БД `osago-aggregator`, события офферов - в брокере, поды агрегатора и `core-app` взаимозаменяемы. Для Websocket перед `core-app` на балансировщике нужна привязка клиента к поду (sticky), чтобы поток не обрывался при переключении инстанса.
